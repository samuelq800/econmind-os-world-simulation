# V09.2 — 候选状态与原子 Commit

## Planning state

- Step state: `PLANNED`.
- Runtime: `NOT_STARTED`.
- Migration: `NOT_CREATED`.
- Execution mode: `NORMAL`.
- Hard dependency: V09.1.

## Authoritative contract

Build a private candidate/checkpoint, recheck the authoritative version, and
commit economic facts, Event, receipt and outbox atomically. The acceptance gate
is: a crash before commit leaves no half-completed economy, and a retry after a
successful commit creates no duplicate economy.

ADR-17 already assigns this transaction boundary to V09. ADR-20 already requires
current authorization to be resolved again at the authoritative transaction;
cached Office context cannot authorize commit. ADR-18's V09.1 evidence gate is
inherited until resolved. ADR-04 remains deferred and does not define this
transaction.

## Candidate boundary

Candidate calculation is private and disposable. It is not authoritative state,
does not emit authoritative Events or Postings, and cannot be externally
observed as committed. The transaction must derive from the accepted Command and
its deterministic V07 lineage while consuming V08 posting rules without
redefining either package.

## Planned authoritative transaction

One logical authoritative transition must execute all-or-zero:

1. begin one short database transaction;
2. lock the World head;
3. verify the live lease holder and fencing token;
4. verify the expected WorldVersion;
5. verify durable V07 idempotency/Command acceptance state;
6. re-resolve current AuthSubject, membership, country, Office, capability,
   authorization revision and approval scope where ADR-20 applies;
7. validate the deterministic candidate and V08 conservation invariants;
8. apply Inventory Posting(s);
9. apply Financial Posting(s);
10. append authoritative Event(s), sequence and hash lineage;
11. store the final receipt linked to the complete Event set;
12. advance WorldVersion exactly once and update current materializations;
13. insert outbox facts at the same committed watermark, then commit.

Any failure rolls back every item. Projection consumers run after commit and may
be retried; they never replay the economic transition.

## Ownership boundaries

- V07 owns Command identity, idempotency, Event identity/order, receipts,
  outbox/consumer receipts and replay lineage. V09 coordinates their atomic
  persistence but does not create competing semantics.
- V08 owns Inventory Posting, Financial Posting, opening/reconciliation rules,
  exact arithmetic and conservation invariants. V09 persists them atomically but
  does not reinterpret their economics.
- V09 owns the authoritative writer transaction, version/fence checks,
  all-or-zero commit and recovery-safe retry behavior.

## Expected persistence surface

The forward migration candidate may need to extend the existing V07 Command,
Event, receipt, outbox and World-head schema with V08 Inventory/Financial
Posting and opening/reconciliation persistence, authoritative constraints, and
a guarded transaction entry point. Exact identifiers remain implementation-time
decisions derived from repository truth; this plan creates no migration.

## Test architecture

P0 transaction tests inject failures at each boundary and prove:

- duplicate retry returns the one durable result;
- partial transaction state is impossible;
- Event without Posting and Posting without Event are impossible;
- an incomplete or mismatched final receipt is impossible;
- WorldVersion mismatch rejects the whole transition;
- stale fencing, lease or authorization at commit rejects the whole transition;
- a crash before commit leaves zero authoritative change;
- a crash after commit but before acknowledgement is recognized as committed;
- concurrent `N -> N+1` attempts cannot both commit;
- deterministic output is stable across process restart.

P1 tests cover deadlock/serialization retry bounds, transaction timeout,
high-cardinality Event sets, and materialization watermark consistency.

## Scope exclusions

No economic rule redesign, alternate Command/Event/Ledger model, asynchronous
partial ledger write, production access, migration creation, runtime
implementation, status change, V09.3 recovery implementation or V10+ work is in
scope.
