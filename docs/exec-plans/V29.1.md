# V29.1 requirements traceability — preparation only

Formal V29.1 entry is blocked by its V22.3–V28.3 hard dependencies in the
current `status/progress.json`; this is not execution or verification.

The immutable source index already contains 8,743 source units, 139 registry
requirements and 131 fixed targets. Before a full-feature claim, each action
must link its source unit and parameters to actual code, authorization,
failure/notification paths, tests, an immutable candidate and review state.
The existing registry's `PLANNED_NOT_IMPLEMENTED` values are stale relative
to merged preparation modules, but they cannot be bulk-promoted merely because
files exist. This preparation records the gap without changing source or
status authority. No original main-site, database or production target is read
or modified.

`tools/v29/requirement-evidence-preparation.ts` provides a strict in-memory
binding matrix: a requirement stays `MISSING` without an explicit claim;
an `EVIDENCED` claim must name one exact candidate SHA and code/test/evidence
paths. The tool validates structure only and always returns
`formallyVerified=false`; independent review and actual artifact existence
remain separate.

Next V29.1 execution: create requirement-by-requirement evidence records,
preserve explicit `MISSING` and `NOT_RUN`, reconcile code candidate SHAs, and
