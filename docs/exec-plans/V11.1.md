# V11.1 — E02 Population Stocks/Flows execution plan

**Status:** `OWNER_AUTHORIZED_IMPLEMENTATION_UNVERIFIED`  
**Baseline:** `626b2e8b25599abbd5b62cdf16a229cf8f6be307`  
**Authority:** `docs/governance/WORLD_CORE_V11_1_CONTINUATION_POLICY.json`

## Boundary and classification

V11.1 is a P0 authoritative-state change: the Population Engine is the sole
writer of population stocks and flows. This plan is a conditional continuation
while Gate B remains `PENDING`; it authorizes a non-production candidate only,
not `VERIFIED`, a main merge, deployment, production/shared-Supabase access,
or migration publication.

The candidate owns only E02 population state:

- country total population, the `0–15`, `16–64`, and `65+` age stocks, and
  household-count stocks;
- explicit birth and death flows; and
- a paired bilateral migration transfer, represented once as an origin outflow
  and once as the destination inflow under one immutable migration identity.

E03 employment, skills, vacancies, wages, participation, job matching and
public staffing remain V11.2. Resources, facilities, services, production,
macro outcomes and UI behaviour remain outside this step.

## Constitutional contract

The implementation must enforce these already-binding rules:

- `Population_t = Population_(t-1) + Births - Deaths + Immigration - Emigration`;
- population cannot be directly increased by a percentage/button or any hidden
  macro adjustment; changes require explicit flow facts;
- every stock is non-negative; and
- Population Engine alone writes population stocks and flows. Labour only reads
  population in V11.2.

ADR-04 and ADR-08 remain `PROPOSED_NOT_APPROVED`. Therefore V11.1 must not
invent demographic-rate formulas, period-input timing, prices, policy
multipliers or an automatic labour supply. It may accept already-explicit,
versioned flow facts and deterministically validate/apply them.

## Candidate design

Implement a pure `packages/core` population transition module. Its inputs must
be immutable population stock and flow values, and its output must be a new
population state plus canonical applied-flow evidence. No browser/API/worker
direct write, persistence adapter, migration, RLS change, external request,
or service credential is in this increment.

The transition must accept only an E01 daily boundary plus explicit,
versioned birth/death, migration-arrival/departure, crisis-flow and permitted
mortality-modifier facts. An approved or scheduled migration is not an arrival
and cannot change either country's population. It must emit canonical evidence
for the implemented population action—birth/death settlement, migration
arrival/departure, household update or age-cohort roll—ready for later mapping
to the existing V07 command/event/receipt path. It must not invent canonical
command types or publish a new persistence path in this increment.

The transition must reject before state change when a flow:

- has an unsupported type, duplicate immutable identity or non-positive count;
- would make a country or cohort stock negative;
- provides only one side of a bilateral migration, has unequal origin/destination
  counts, or changes either side after canonicalization; or
- conflicts with a previously recorded canonical flow identity.

Deterministic ordering must be explicit and stable. Reapplying the same
canonical flow set must return the same result; a same-identity, different
payload must fail closed. Household counts may be represented only as a
non-negative stock carried by explicit flow facts; no household composition or
labour allocation model is introduced here.

A dependency ratio may be derived from the three age stocks but is never an
independently writable input. If a household recomputation disagrees with the
explicit population flow result, it must emit a reconciliation warning and
must not silently alter total population. A migration arrival may carry typed
handoff metadata for V11.2, but it must not create an authoritative labour
force, skill, wage, vacancy, job-match, public-workforce or downstream-service
state.

## Required evidence before handoff

1. Focused unit/invariant tests for birth, death, domestic no-op, and paired
   cross-country migration; prove the stock-flow identity per country/cohort.
2. Negative tests for underflow, unilateral or mismatched migration, duplicate
   identity conflict, scheduled-but-not-arrived migration, and any attempt to
   create population without a flow.
3. Determinism/idempotency tests over differently ordered but identical input
   sets and exact retries.
4. Tests that household reconciliation cannot alter population, dependency
   metrics are derived only, and typed migration handoff data cannot become a
   V11.2 labour state.
5. Applicable TypeScript, lint, formatting, core build, boundary, governance
   and secret checks. Record actual commands and results; retain `NOT_RUN` if a
   check cannot run.
6. `docs/reports/V11.1/IMPLEMENTATION.md` and `TEST_EVIDENCE.json`, bound to
   the immutable candidate, naming no schema/RLS/command/event publication.

## Stop conditions and handoff

Stop for any P0/MAJOR finding, failed mandatory test, requirement for a
demographic formula or period-input rule, persistence/schema/RLS mutation, or
any dependency on V11.2. Do not start V11.2 from this plan. The final V11.1
candidate requires independent review before it can be marked `VERIFIED` or
promoted.
