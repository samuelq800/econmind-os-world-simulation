## Purpose and acceptance gate

Exact R2 purpose:

> 建立 command_id、event_id、payload hash、simulation/real timestamps、append-only event store。

Exact R2 acceptance gate:

> 同ID异payload拒绝；历史 event 不 UPDATE/DELETE。

The smallest implementation satisfying that gate establishes canonical,
versioned Command and Event envelopes; stable identity and payload
fingerprinting; distinct simulation and real-audit timestamps; and an ordered,
append-only event persistence boundary. It does not implement economic engines
or the later receipt, outbox, replay executor, lease, or transaction packages.

## Source-law anchors

- Constitution U0206 and U0646: the same initial state, commands, events, and
  seed must produce the same output.
- Constitution U0209-U0214 and U0648-U0650: scheduled work is idempotent; every
  Command and Event has a unique ID; repeated network requests and processing
  state must be auditable.
- Constitution U0217-U0220 and U0652-U0653: one economic fact is recorded once;
  correction is a new Event and never a rewrite of an old ledger Event.
- Constitution U0471-U0475: UI writes use authoritative Commands; snapshots are
  accelerators and cannot replace ledger/current-table authority; performance
  cannot weaken atomicity, RLS, idempotency, reconciliation, or Source of Truth.
- Master U0079-U0081: `ImmutableEventLedger` is the append-only history within
  the single World State; correction uses reversal/correction Events.
- Master U0193-U0196 and U0205-U0223: E01 owns scheduled identity/order and
  idempotency keys; duplicate delivery/payment cannot execute twice.
- Master U1918: the broad event audit vocabulary is a source requirement, but
  final V07.1 field names and nullability remain subject to approved ADR-11/17
  and schema review.

Source-unit registration is traceability, not an implementation claim.

## Ownership boundaries

### Command ownership

- `packages/core` owns the pure, canonical Command envelope, branded Command ID,
  schema/version registry contract, and deterministic fingerprint preimage.
- `apps/world-api` is the authentication and Command/query boundary. It may
  validate and persist an immutable submission through the controlled intake
  path, but it may not execute economic mutations or assign Event order.
- External `AuthSubject` remains a canonical UUID distinct from resolved World
  `ActorId`, `CountryId`, and `OfficeId`. Claimed routing values never replace
  server-side resolution.
- `apps/world-web`, the main site, V1/Legacy, caches, projections, snapshots,
  replay views, and forecasts cannot own or directly mutate a Command outcome.

Under approved ADR-11, the fingerprint must cover every authoritative
intent field and exclude transport/real-audit metadata. It must use the repaired
V03 inert canonical serialization and fixed SHA-256 preimage convention. The
same Command ID or idempotency identity with different authoritative intent
must fail with zero authoritative mutation.

### Event ownership

- `packages/core` owns the pure Event envelope and versioned Event-type/schema
  contracts.
- `apps/world-worker` is the authoritative execution host and is the only
  component allowed to assign per-World Event sequence/order inside the later
  controlled commit path. Clients never provide ordering.
- Event history is append-only. UPDATE, DELETE, resequencing, or overwriting a
  correction is forbidden; correction/reversal is a new Event.
- Operational errors and delivery status are not economic ledger Events.

The planned minimum Event envelope preserves `eventId`, `worldId`, per-World
sequence, `WorldVersion`, causation Command identity, correlation identity,
SimTime, Event type, schema version, and canonical payload. This is a planning
shape from the current World Core contract and approved ADR-17 boundary.

### Receipt semantics and scope split

V07.1 establishes only the identities and immutable references that later
receipts require. V07.2 owns accepted-versus-executed semantics, immutable
acceptance acknowledgement/final receipt, durable duplicate-return behavior,
consumer receipts, outbox, queue/claim, and delivery deduplication. Accordingly:

- V07.1 may reject same-ID/different-payload at its boundary.
- V07.1 must not claim that the final receipt/outbox lifecycle is implemented.
- Event `processed_at` or consumer state must not be implemented by updating a
  historical Event; V07.2 will use a separate consumer receipt/delivery record.
- ADR-20 must be approved before V07.2 queues a Command; no acceptance-time
  context becomes execution authority in V07.1.

### Replay requirements and scope split

V07.1 must preserve replay-complete immutable facts: stable sequence,
WorldVersion transition, causation, SimTime, type/schema version, canonical
payload, and verifiable canonical bytes/hash material. It must fail closed on
unsupported versions and structurally corrupt ordering rather than creating a
best-effort history.

V07.3 owns the replay executor, opening-seed provenance, reducer registry,
seeded RNG interface, engine/model/registry version binding, contiguous replay,
and live-versus-replayed hash comparison. Snapshots/checkpoints remain
rebuildable accelerators and never become a second Source of Truth.

### Authoritative writer boundary

The only state-change path remains:

```text
authorized command
-> validated receipt/idempotency
-> deterministic worker
-> atomic append-only events/postings
-> derived projections
```

For V07.1, this means the API can own immutable intake and the Worker alone can
assign authoritative Event order. The durable per-World lease, fencing token,
stale-writer rejection, private candidate, WorldVersion recheck, and atomic
economic/Event/receipt/outbox commit are V09.1-V09.2 responsibilities. V07.1
must leave enforceable interfaces for those later guarantees without claiming
them as implemented.

## Dependency on V06 SimTime and scheduler

- Command/Event SimTime fields must use V06's branded, non-negative integer
  simulation-millisecond ticks; real timestamps are audit/operational metadata
  only and cannot determine an economic deadline or outcome.
- The scheduler's approved total order remains
  `(dueSimTime, priorityRank, scheduledEventId)`. V07.1 does not replace it with
  network arrival, database row order, object iteration, or wall-clock order.
- A scheduled identity completed by V06 can causally produce ordered ledger
  Events, but `ScheduledEventId` and economic `EventId` remain distinct types.
- V06's command cutoff is the immutable SimTime observed when the Worker begins
  the authoritative transaction. V07.1 records compatible identities/time
  values; V09 owns that transaction.
- PAUSED contributes zero SimTime and RUNNING downtime uses deterministic
  catch-up. Ledger replay must consume the recorded canonical advancement and
  scheduling outcomes, never recompute them from ambient wall time.

## Deterministic and idempotent requirements

1. Equivalent inert canonical envelopes produce identical fingerprint bytes;
   field insertion order, transport metadata, and server audit time cannot
   change economic identity.
2. Getter, method/provider, Proxy, hidden/symbol state, sparse array,
   unsupported prototype/container, JS-number exact value, and unknown schema
   versions fail closed before behavior or mutation.
3. `commandId`, `eventId`, schema/type IDs, SimTime, and WorldVersion remain
   branded/canonical; `AuthSubject` cannot be substituted with a domain ID.
4. Same ID with different authoritative payload/fingerprint is a deterministic
   conflict with no new Event or WorldVersion transition.
5. Event sequence is unique and contiguous per World at the controlled writer
   boundary; insertion/network order cannot select it.
6. Historical Event bytes are immutable. Correction adds a causally linked
   Event and never edits or deletes the original.
7. In-memory duplicate tracking, last-write-wins, payload-only comparison, or a
   client-supplied order is never authoritative.

Exact same-payload retry returning the stored acknowledgement/final receipt and
never re-executing is the approved ADR-11 target and required by the V07
package gate, but its durable end-to-end implementation belongs to V07.2/V09.
It must not be reported as delivered by V07.1 alone.

## P0 risks

- Drifting from approved ADR-11 duplicate/fingerprint/receipt semantics or
  approved ADR-17 persistence/writer/replay semantics.
- A second Source of Truth, direct UI/API economic write, or client-selected
  Event order.
- Same identity with different intent being accepted, overwritten, or treated
  as a retry; or duplicate delivery creating a second economic fact.
- Mutable ledger history, consumer state stored by updating Events, silent
  correction, non-contiguous/resequenced Event history, or replay corruption
  being skipped.
- Mixing wall time with SimTime, losing the V06 scheduler order/cutoff, or
  conflating ScheduledEvent and economic Event identities.
- Behavioral/non-canonical fingerprint input, JS-number exact values, unknown
  versions, or hash ambiguity.
- Promoting/merging candidate DDL without ADR-16 approval, or building it
  without V02 manifest provenance, isolated rehearsal, worker-only authority,
  or production-safety evidence.
- Claiming atomicity, single-writer enforcement, durable exactly-once effects,
  receipts, outbox, or replay before V07.2/V07.3/V09 supplies them.

Any P0 failure stops V07.1 and requires correction plus the policy-required
independent review of an immutable candidate. The implementer cannot self-mark
the step `VERIFIED`.

## P1 risks

- Public API ergonomics or registry layout accidentally freezing future Command
  families beyond the minimum versioned contract.
- Payload/envelope growth or index choices creating avoidable storage and
  lookup cost without changing correctness.
- Error names, module layout, or exported helper surface coupling V07.1 to
  future E02-E18 behavior.
- Test fixtures or generated declarations drifting from the canonical source
  contract while runtime behavior remains unchanged.

P1 issues may follow only the repository's explicit review policy; they cannot
be used to downgrade a change that also touches a P0 boundary.
