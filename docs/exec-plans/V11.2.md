## Boundary and classification

V11.2 is a P0 authoritative-state change. E03 is the sole owner of labour
status, skill stock, sector employment, vacancies, wage facts, matching flows,
and public-service workforce allocation. The owner-authorized continuation
permits an immutable, non-production candidate only. It does not authorize
`VERIFIED`, a main merge, deployment, shared-Supabase access, a migration,
RLS, an API/worker/UI path, or V11.3+ work.

The candidate owns only a pure E03 state/fact transition in
`packages/core/src/labour/`, its core export, one focused test suite, and
V11.2 plan/evidence reports. It will not import or merge the parallel F
kernel. The F kernel is a design reference only; this candidate establishes
the authoritative state boundary required by the V11.2 contract.

## Constitutional contract

The E03 source contract requires `LabourPersonAggregate` by skill, status and
location; sector labour demand/employment/vacancy; wage state; matching; and
public-service labour. It requires all employment allocations to sum to total
employed, skill transitions to conserve people, vacancies to be filled only by
actual compatible workers, and public hiring to consume the same labour pool as
industry.

The E02 input is read-only working-age availability. It does not create a
labour status, a worker, labour-force participation, or a skill stock. Skill
can enter E03 only through explicit, versioned education-transition or
migration-work-right facts. Each job demand, match, separation, public-service
occupation and wage assertion has an immutable fact ID and canonical payload;
an exact retry is a no-op and a same-ID different payload rejects.

## ADR cut line

ADR-04 and ADR-08 remain `PROPOSED_NOT_APPROVED`.

- No opening/current/prior-day phase selection, current-period feedback, or
  wage-price-demand loop is encoded.
- No participation, matching or wage formula, default coefficient, implicit
  matching capacity, default minimum wage, rate calculation, economic rounding
  rule, or decimal-precision policy is introduced.
- A job match is accepted only when an explicit fact supplies an exact count,
  matching skill/location, and referenced vacancy. A wage is recorded only as
  an explicit versioned canonical decimal string; the core neither calculates
  nor settles it as money.
- If an input would require one of those unresolved decisions, it fails closed
  before a result exists.

## Candidate design

`applyLabourFacts` receives a caller-created E01 daily-boundary token, immutable
E03 state, an explicit read-only population availability snapshot, and explicit
facts. It returns canonical new state plus applied-fact evidence. It has no
persistence, command, event, receipt, database, schema, external request, or
service credential boundary.

The initial state has canonical aggregates keyed by country, location and skill
for `UNEMPLOYED_SEARCHING`, `EMPLOYED`, `NOT_IN_LABOUR_FORCE` and `STUDENT`;
private sector positions; public-service positions; explicit versioned wage
facts; and durable applied-fact bindings. The aggregate source and each
position are reconciled on every input and result:

- every count is a canonical non-negative whole-person count;
- aggregate employed equals the sum of private-sector plus public-service
  employment for the same country/location/skill; and
- the sum of all labour-status aggregates cannot exceed the supplied read-only
  working-age availability for that country/location. No population field is
  mutated or cached as a second source of truth.

The only accepted mutations are:

1. education skill transition and migration labour entry, which explicitly
   create an `UNEMPLOYED_SEARCHING` aggregate with a stated skill and location;
2. job demand upsert, which creates/changes only an explicit position's
   required headcount and derives its vacancy from required minus employed;
3. exact job match, which moves the stated count from an existing unemployed
   aggregate to one compatible private-sector position;
4. separation, which moves employed people from an existing private or public
   position back to the matching unemployed aggregate;
5. public occupation, which moves people from an existing unemployed aggregate
   into an explicit public-service position; and
6. wage assertion, which records a supplied `wageVersion` and non-negative
   canonical decimal amount against an existing position without calculating
   compensation, price, tax, payroll or settlement.

No implicit participation, first-time population-to-labour conversion,
job creation, matching, wage uplift, worker reclassification, public budget
approval, location mobility, education completion, migration arrival, or
automatic position closure exists. There is no pending queue, timing selection,
or future-dated activation in this step.

Within one input set, a position or aggregate may have only one active mutation
fact. A match may not depend on a demand, education, migration or separation
fact from the same set. This intentionally rejects intra-boundary chaining
rather than deriving an unapproved timing order from immutable IDs; callers
must supply the already-settled state as the next explicit transition input.

## Required evidence before handoff

1. Focused tests prove deterministic canonical ordering, exact retries, and
   same-ID different-payload rejection for every implemented fact class.
2. Tests prove read-only population cannot create labour, skill has only the
   education/migration fact paths, and invalid/missing explicit facts fail
   closed.
3. Tests prove match and public occupation consume the shared unemployed pool;
   skill/location mismatch, vacancy overfill, repeated allocation, separation
   underflow, and mismatched aggregate/position state reject before a result.
4. Tests prove explicit wage versions are canonical/non-negative, are bound to
   an existing position, and do not calculate money, payroll, price or rates.
5. Run focused tests, core typecheck/build, scoped lint/format, authoritative
   pattern, boundary, foundation-policy, environment and secret checks. Record
   actual outcomes and retain `NOT_RUN` honestly.
6. Produce V11.2 implementation and test-evidence reports bound to the
   immutable candidate, explicitly stating independent review remains required.

## Stop conditions and handoff

Stop for any P0/MAJOR finding, failed mandatory check, need for a population
timing rule, a participation/matching/wage formula, an economic rounding rule,
or any persistence/API/worker/schema/migration/production requirement. The
final candidate remains `IMPLEMENTED_UNVERIFIED` and must receive independent
V11.2 review before it can be marked `VERIFIED` or promoted. V11.3+ remains
out of scope.
