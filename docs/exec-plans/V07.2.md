## Planned ownership boundaries

### Command queue and authorization

- The API owns authenticated Command intake, canonical intent fingerprinting,
  durable idempotency lookup, and an immutable acceptance acknowledgement. It
  does not execute authoritative economic effects.
- The worker owns operational queue claim and dispatch. Immediately before a
  protected user-command transaction, the authoritative server boundary must
  re-resolve current identity, membership, country, Office, capability,
  suspension state, authorization revision, and applicable `WorldVersion`.
- Intake authorization context is audit evidence, not execution authority.
- The browser, client, ordinary application role, notification consumer, and
  outbox dispatcher are never authoritative World State writers.

### Idempotency

- The idempotency record is durable and survives API or worker restart; an
  in-memory cache is not authoritative.
- The same world, idempotency identity, and canonical intent fingerprint returns
  the stored acceptance/final result without re-executing the Command.
- Reuse of the same key or Command identity with a different fingerprint is a
  deterministic conflict with zero economic mutation.
- Sequential retries, concurrent retries, a dropped response, recovery, and
  outbox redelivery must preserve exactly one economic effect.

### Events, receipts, and outbox

- Acceptance acknowledgement and final execution receipt are distinct durable
  records. Acceptance does not assert that economic execution committed.
- The immutable final receipt records the outcome (`COMMITTED`, `REJECTED`,
  `DUPLICATE`, or `CONFLICT`), reason, intent fingerprint, relevant version and
  SimTime facts, and emitted Event identifiers.
- A rejected or conflicting Command produces no authoritative economic mutation.
- Immutable economic Events are separate from consumer delivery/receipt state.
  Consumers may update only their own operational delivery state.
- Outbox retries may redeliver a notification, but cannot replay an economic
  mutation or rewrite the immutable Event or final receipt.

### Exact reads and writes

- Reads: immutable `command_submission`, any stored final Command receipt,
  current World/membership/Office/capability and authorization revision,
  expected WorldVersion, referenced Event identities, queue state, outbox
  delivery state, and consumer-specific receipt state.
- Authoritative writes: one immutable acceptance identity and at most one
  immutable final Command receipt. Event/economic writes remain outputs of the
  later authoritative transaction boundary and are never performed by an
  outbox or consumer handler.
- Operational writes: one queue row per accepted Command, claim/attempt state,
  outbox delivery attempts, and per-consumer delivery receipts. Operational
  state cannot determine an economic amount, due date, fingerprint, Event
  history, or committed outcome.
- Queue authority kinds are explicit: pending discretionary user work requires
  commit-time reauthorization; a durable versioned automatic obligation follows
  its governing version/cancellation rule and must not be retroactively
  invalidated by later actor authority loss.

### Receipt and recovery state machine

- Acceptance is `ACCEPTED` and does not claim execution. An exact duplicate
  returns the original acknowledgement or stored final receipt; it does not
  create a new logical queue item or receipt.
- Final outcomes are versioned and deterministic: `COMMITTED`, `REJECTED`,
  `AUTHORIZATION_REVOKED`, and `IDEMPOTENCY_CONFLICT`. Duplicate is response
  semantics pointing to the original record, not a second authoritative final
  receipt.
- Recovery of pending or claimed discretionary work repeats current authority
  resolution before any authoritative commit. Authorization failure produces
  `AUTHORIZATION_REVOKED`, zero authoritative effect, and no Event IDs.
- Recovery/replay of a committed fact returns its stored receipt and does not
  retrospectively reauthorize the original actor. V07.3 replays committed
  Events, not pending queue attempts.

### Persistence and authoritative writer boundary

- Authoritative Command/idempotency/receipt/Event state is written only by the
  trusted server-side World Core transaction boundary.
- Candidate persistence artifacts remain in the V02-governed `world_v2`
  namespace and migration manifest with commit, path, and byte-hash provenance.
- Any branch-local candidate DDL remains unpromoted until ADR-16 is approved;
  this plan grants no migration publication or production authority.
- V09 owns lease/fencing mechanics and the final all-or-zero authoritative
  transaction coordinator. V07.2 must define storage and interfaces that can be
  consumed by that boundary without pretending to implement V09.

## Test matrix

| Case                                            | Required result                                                                      |
| ----------------------------------------------- | ------------------------------------------------------------------------------------ |
| First valid Command                             | One acceptance record; at most one final economic effect and immutable final receipt |
| Sequential exact duplicate                      | Stored result returned; no second economic effect                                    |
| Concurrent exact duplicate                      | One winner/effect; all callers converge on the durable result                        |
| Same key or identity with different fingerprint | Deterministic conflict with zero economic mutation                                   |
| Response lost after acceptance or commit        | Retry recovers the stored acknowledgement or receipt without re-execution            |
| API or worker restart                           | Durable idempotency records prevent a second economic effect                         |
| Authority revoked or changed while queued       | Approved ADR-20 policy is applied; stale intake context is not authority             |
| Rejected Command                                | Immutable rejection receipt and zero economic mutation                               |
| Outbox redelivery                               | Notification may repeat but economic mutation and immutable Event may not            |
| Consumer duplicate delivery                     | Only that consumer's operational receipt state may change                            |
| World or contract version mismatch              | Deterministic rejection with no silent fallback                                      |
| SimTime or scheduling interaction               | Consume V06 authority without creating a second clock or ordering rule               |
| Malformed receipt/outbox or unknown version     | Fail closed before persistence or dispatch                                           |
| Pending discretionary recovery                  | Re-resolve current authority before commit; revoked work records zero-effect outcome |
| Already committed fact after revocation         | Return durable fact/receipt without retrospective authorization                      |

## Determinism, replay, and compatibility

- Command identity, fingerprinting, conflict classification, stored-result
  lookup, receipt contents, and retry outcomes must be deterministic.
- V07.2 records all inputs and version references needed by V07.3 replay, but
  V07.3 owns the replay executor, seeded RNG policy, version binding, and replay
  hash comparison.
- V06 remains the sole authority for SimTime and scheduler ordering. V07.2 may
  persist or reference those facts but cannot redefine them.
- V09 compatibility requires explicit `WorldVersion` and later lease/fence
  fields or interfaces. V07.2 does not implement V09's lease, fencing, or atomic
  transaction coordinator.

## Risks

### P0

- Queued discretionary work executes after the actor loses relevant authority.
- Concurrent duplicates produce more than one economic effect.
- Candidate DDL is merged or promoted before ADR-16 approval or outside the V02
  publication chain.
- Event, mutation, final receipt, and outbox records cannot later participate in
  V09's all-or-zero authoritative transaction.

### P1

- Acceptance acknowledgement is mistaken for a final execution receipt.
- Consumer delivery state can mutate immutable Events.
- Receipts omit version, SimTime, fingerprint, or Event evidence needed by V07.3.
- V07.2 storage assumptions conflict with V09 lease and fencing mechanics.
