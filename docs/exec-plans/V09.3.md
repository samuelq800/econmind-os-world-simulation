# V09.3 — 故障注入与恢复矩阵

## Planning state

- Step state: `PLANNED`.
- Runtime: `NOT_STARTED`.
- Migration: `NOT_CREATED`.
- Execution mode: `NORMAL`.
- Hard dependency: V09.2.

## Authoritative contract

Cover lease expiry, old WorldVersion, database and Worker crashes, notification
interruption and checkpoint recovery. The acceptance gate is that authoritative
state is recoverable and replayable.

## Recovery architecture

- Uncommitted candidate and transaction state disappears on rollback/restart.
- A claimed Command with no final receipt can be reclaimed only after the old
  lease is no longer authoritative and a higher fencing token is held.
- A committed transition is recognized from durable idempotency, receipt,
  Event/Postings, WorldVersion and watermark state; retry returns the stored
  result instead of reapplying economics.
- Outbox delivery retries independently from the authoritative commit. Failure
  after commit cannot cause economic replay.
- World head, Event sequence, Posting lineage, receipt and outbox watermark are
  reconciled before writer service resumes.
- Current materializations can be rebuilt from the V08 opening seed and ledgers
  through the V07 authoritative Event/replay lineage; process memory is never a
  recovery authority.

## Failure matrix

P0 evidence must exercise realistic engineering failures:

- two writers for one World;
- stale lease holder and stale fencing token;
- duplicate retry;
- exception or connection loss during a partial transaction;
- attempted Event-without-Posting and Posting-without-Event states;
- inconsistent receipt/Event set;
- WorldVersion mismatch;
- Worker or database crash before commit;
- Worker crash after commit but before acknowledgement;
- outbox delivery failure and retry;
- restart recovery and deterministic replay;
- stale authorization at commit where ADR-20 applies;
- checkpoint/watermark mismatch and projection rebuild.

P1 evidence covers bounded transaction retries, repeated takeover, delayed
renewal, corrupt non-authoritative cache/materialization, large replay windows,
and multi-World recovery isolation.

The matrix must use real PostgreSQL and separate processes/connections where
concurrency or crash semantics matter. Final environment-specific evidence is
subject to the ADR-18 JIT gate; unit-only simulation is insufficient.

## Expected persistence impact

V09.3 should add no speculative migration. A forward migration is permitted only
if the failure matrix proves a concrete recovery/checkpoint invariant cannot be
represented by the V09.1/V09.2 schema, and it must pass the same branch-local,
hash-bound and clean/existing rehearsal gates.

## Scope exclusions

No open-ended attack campaign, production fault injection, economic rule
redefinition, new Command/Event/Ledger semantics, runtime implementation,
migration creation, status change or V10+ work belongs to this planning step.
