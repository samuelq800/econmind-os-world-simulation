# V00.3 Execution Plan

## Contract and gate

V00.3 is **Startup-Layer Integration Verification and Bootstrap Report** in S0,
execution mode `NORMAL`. Its hard dependency, V00.2, is `VERIFIED` on merged
`main` at `20e2ab40bb779274fc8812073fb4dbe401a8e420`. The authorized purpose is
limited to Web-to-API health communication, operational Worker readiness
verification, one unified development command, and bootstrap evidence.

The exit gate is automatic proof of the three application runtime boundaries
without business-database writes. This step remains implementation-only and
will stop at `IMPLEMENTED_UNVERIFIED` pending independent review.

## Scope and ownership

Affected owners are:

- `WORLD_WEB`: add one server-side development health dependency probe under
  `GET|HEAD /__bootstrap/api-health`.
- `SERVER_ONLY`: add the unified development bootstrap coordinator and its
  fixed operational configuration, polling, evidence, and shutdown logic.
- `WORLD_API` and `WORLD_WORKER`: read their existing V00.2 `/readyz` surfaces;
  do not add domain, command, persistence, or cross-service ownership.
- repository test/governance tooling: cover the real `pnpm dev` boundary and
  preserve the existing V00.1/V00.2 checks.

The coordinator composes the existing public commands:

```text
pnpm dev
  -> server-only bootstrap coordinator
     -> pnpm dev:web
     -> pnpm dev:api
     -> pnpm dev:worker
```

It does not replace the per-application V00.2 lifecycle owner.

## Reads, writes, commands, and events

Runtime reads are limited to approved local host/port/environment values,
child-process state, OS signals, and fixed local HTTP readiness responses.
Runtime writes are limited to child process control, sanitized operational HTTP
responses, and JSON-line bootstrap evidence on stdout/stderr.

No World State, economic state, simulation time, database row, file-backed
state, cache, or Supabase resource is read or written. No domain command or
domain event is emitted or consumed. Lifecycle messages such as
`BOOTSTRAP_READY` are operational evidence, not domain events.

## Web-to-API dependency probe

The Web runtime owns a server-side operational endpoint at
`/__bootstrap/api-health`. Its API target is constructed only from the existing
approved API host/port configuration and the fixed `/readyz` path. One endpoint
invocation performs exactly one request with a bounded timeout, no redirect,
no internal retry, and no success cache. It returns only:

```json
{"service":"world-web","dependency":"world-api","status":"ok"}
```

with HTTP 200 on a validated API-ready response, or the same fixed schema with
`status: "unavailable"` and HTTP 503. It never discloses an upstream URL, host,
port, error, environment value, response body, or secret. Unsupported methods
return 405. This reserved development endpoint does not establish an `/api/*`
business proxy and does not approve ADR-19.

## Bootstrap lifecycle

Lifecycle phase and terminal outcome are separate:

```text
phase: STARTING | WAITING_FOR_DEPENDENCIES | READY | SHUTTING_DOWN | STOPPED
outcome: SUCCESS | FAILED | CANCELLED
```

Failure evidence retains `failed_service`, `failure_reason`, `exit_code`, and
`signal` where applicable after cleanup reaches `STOPPED`.

The bootstrap readiness loop uses a fixed polling interval and global startup
deadline. Each poll executes independent one-shot bounded probes for Web, API,
Worker, and Web-to-API health. Immediately before aggregate readiness, the
coordinator rechecks all three child processes and repeats all dependency
probes so earlier success cannot become stale. `BOOTSTRAP_READY` is emitted
exactly once only after this final commitment succeeds.

Any invalid configuration, occupied port, startup error, premature exit,
timeout, shutdown signal during startup, or post-ready child crash moves to a
failure or cancellation outcome and bounded cleanup. Repeated signals cannot
bypass cleanup. The coordinator uses fixed commands with `shell: false`, owns
only its three public launcher children, and preserves per-application
parent-loss cleanup.

## Test strategy

Integration acceptance starts the real public `pnpm dev` command on isolated
loopback ports. Tests verify:

- three real application processes and all local `/readyz` surfaces;
- Web-to-API health and Worker readiness participation;
- exactly one aggregate `BOOTSTRAP_READY` event;
- Web/API/Worker partial-start failures, invalid env/host/port, occupied port,
  child exit before readiness, readiness timeout, and unexpected runtime crash;
- SIGINT, SIGTERM, and repeated signals during startup/cleanup;
- bounded cleanup, descendant termination, endpoint closure, and port reuse;
- TOCTOU rejection when API readiness succeeds and API exits immediately before
  the final readiness commitment;
- arbitrary URL, redirect, protocol, path, port, and shell injection rejection;
- no `shell: true`, secret/service-role disclosure, upstream error disclosure,
  cached success, broad CORS, credential forwarding, database, or Supabase use.

The existing V00.1 and V00.2 regression suites remain enabled. Repository lint,
format, typecheck, unit/integration, boundary, environment, secret, build,
governance, and whitespace checks will run with the pinned toolchain.

## Failure and recovery

Cleanup has a bounded graceful period followed by an owned-child kill fallback.
Tests must demonstrate that all application descendants terminate and the three
ports become reusable. Successful cleanup never rewrites a `FAILED` outcome as
`SUCCESS`. A normal post-ready developer shutdown is `SUCCESS`; a requested
shutdown before readiness is `CANCELLED`; configuration, startup, dependency,
or runtime failures are `FAILED` with deterministic nonzero exit where the
coordinator controls the exit.

## Data, security, and future-scope exclusions

- Database/Supabase access, mutation, migration, seed, backfill, RLS, Realtime
  business state, and production mutation: **NONE**.
- World State, Simulation Clock, economic tick, command/event ledger, Office
  commands, settlement, economic orchestration, V01 requirement registry,
  V25 UI/map, V26 forecast/cache, V27 country initialization, and V28
  World/Season orchestration: **EXCLUDED**.
- ADR-01 through ADR-20 remain `PROPOSED_NOT_APPROVED`.
- Legacy application behavior and production deployment are unchanged.
