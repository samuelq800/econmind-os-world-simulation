# V21.3 — Logistics Bottleneck and Trade Replay Foundation Candidate

## Status and boundary

`FOUNDATION_IMPLEMENTED_UNVERIFIED`. V21.2 has no independent review or
authoritative integration evidence in this worktree. The module does not create
a shipment, transit inventory record, delivery event, inventory posting,
reservation, command, worker or persistence operation.

## Scope

- Validate caller-owned in-transit shipment, bottleneck and reported outcome
  facts using exact commodity quantities and simulation-millisecond times.
- Allow only partial delivery/loss within all three explicit remaining port,
  rail and storage capacities; reject delivery after expiry.
- Return destination availability only for reported delivered quantity. In-transit
  quantity itself never becomes usable inventory.
- Emit a deterministic immutable replay proof with no second state store.

## Owners and exclusions

Logistics remains the future lifecycle owner; Port/Rail/Storage capacity sources
remain external owners; Inventory remains the stock owner; Trade owns contracts.
No route, latency, loss, capacity, expiry, partial-fill or transit default
formula is selected by Core.

## Evidence target

Focused tests prove physical bottleneck enforcement, partial delivery/loss,
in-transit non-availability and replay equality. Core typecheck/build, focused
regressions, boundary and secret checks are required before review.
