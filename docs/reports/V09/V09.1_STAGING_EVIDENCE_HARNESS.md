# V09.1 Dedicated Non-Production Staging Evidence Harness

## Status and boundary

```text
V09.1 = IN_PROGRESS
V09.2 = NOT_STARTED
remote staging mutation by this implementation = NOT_RUN
production/shared Supabase access = NOT AUTHORIZED
```

This is a fail-closed local harness for the remaining ADR-18 evidence. It does
not use the repository's linked Supabase project, does not invoke the Supabase
CLI, and has no default approved target or credential.

## Exact non-secret approval contract

Before even a dry-run, a later owner-approved, version-controlled file must
exist at exactly:

```text
config/v09-staging-target.json
```

It must use schema version `V09_DEDICATED_STAGING_TARGET-2` and bind the exact
20-character project ref, canonical database host and port, database name,
admin role, `world_v2` namespace, and these exact non-login roles:

- `v09_staging_migration_owner`
- `v09_staging_worker`
- `v09_staging_reader`

The contract must state `DEDICATED_NONPRODUCTION`, explicitly set both
`production_target` and `shared_target` to `false`, carry the owner confirmation
`OWNER_APPROVED_DEDICATED_NONPRODUCTION_V09`, and contain the deterministic
target fingerprint over those fields plus one absolute, normalized,
owner-approved local `evidence_output_path` ending in `.json`. Environment
project refs, hosts, and output paths are not accepted as substitutes for this
contract.

## Dry-run command

```bash
pnpm v09:staging:plan
```

`plan` is always dry-run only. The candidate also exposes
`pnpm v09:staging:execute`, but that command is not an approval to run it: it
fails closed unless the exact owner contract, one-shot confirmation, fingerprint
and secret admin URL all pass policy before a connection factory is invoked.
There is deliberately no standalone broad cleanup command.

## One-shot execution and cleanup candidate

The candidate runner may execute only after it requires all of:

| Input                                | Secret? | Required value / purpose                                                                 |
| ------------------------------------ | ------- | ---------------------------------------------------------------------------------------- |
| `ECONMIND_ENV`                       | No      | exactly `staging`                                                                        |
| `V09_STAGING_TARGET_FINGERPRINT`     | No      | exact contract fingerprint                                                               |
| `V09_STAGING_EXECUTION_CONFIRMATION` | No      | `EXECUTE_OWNER_APPROVED_V09_STAGING`                                                     |
| `V09_STAGING_ADMIN_DATABASE_URL`     | Yes     | securely provisioned PostgreSQL admin connection, exact approved host/port/database/role |
| `evidence_output_path` in contract   | No      | exact owner-approved local path for one redacted durable JSON evidence handoff           |

The connection string must use exactly the literal query `?ssl=true`, with no
fragment, second query parameter, duplicate, encoding variant or TLS override.
The policy instantiates `pg.Client` without connecting and verifies that its
effective host, port, user, database and TLS state match the approval contract.
The connection is passed through the approved secret channel only; it is never
printed, committed, or accepted from a publishable/anon key.

## Candidate evidence plan

It first validates the exact branch-local `0001`–`0006` chain locally, rejects
any linked Supabase project, any existing `world_v2` schema or dedicated role,
and only then creates the three named NOLOGIN roles. It creates `world_v2`
under the migration-owner role, writes a run marker, applies the exact artifacts
and release ledger, and tests:

- active single-World second-writer rejection;
- DELETE/TRUNCATE rejection, expiry takeover to fence `2`, and stale-fence
  rejection;
- crash before commit rollback and crash after commit recovery;
- schema/table ownership, PUBLIC revocation, Worker least privilege, Reader
  read-only behavior, and enabled/forced RLS.

The main setup transaction is rolled back if it fails before commit. After a
successful or commit-ambiguous marker write, a fresh cleanup connection verifies
the exact current-run marker, role names, namespace ownership, allowlisted
object inventory, role residue and absence of user-namespace dependents. It
then removes only the known `0006` through `0001` objects and runner marker in
reverse construction order, with `RESTRICT` on every schema/object drop. It
revokes only the runner-created memberships and drops only the three exact
NOLOGIN roles after their shared dependencies are absent. It never issues
`CASCADE`, `DROP DATABASE`, `DROP OWNED`, a reset, cross-schema deletion, or an
unscoped cleanup. Any unexpected object, public/operator or other external
dependency, mismatch, residue, or teardown failure reports
`CLEANUP_INCOMPLETE` for manual owner direction.

The acknowledgement-unknown evidence is not inferred from a client close. The
dedicated non-production primary sends `COMMIT; SELECT pg_sleep(...)`; an
independent recovery/admin connection must verify the exact primary PID in
post-commit `PgSleep` and terminate that exact PID before recovery reads the
exact committed marker. Missing visibility or termination authority reports
`CRASH_PROTOCOL_UNAVAILABLE`, never a passing evidence result. After cleanup,
the runner writes redacted evidence to the contract's exact local path by
temporary file, file sync, atomic rename, and parent-directory sync. A write
failure is `DURABLE_EVIDENCE_WRITE_FAILED` and cannot change the cleanup duty.

The supplied current parent/default project is rejected because the contract
does not prove it is dedicated non-production. A client publishable or anon key
is insufficient and rejected; only the admin PostgreSQL connection is accepted.

## Cleanup and recovery boundary

The one-shot runner cleans up in `finally` only after a marker might have
persisted. Its recovery cleanup requires the same target contract, fingerprint,
confirmation and admin connection. It first verifies the exact run marker and
the full known-object/role boundary, then removes only the allowlisted
`world_v2` objects by `RESTRICT` and the three named roles. It must never run a
database reset, `CASCADE`, a database drop, or an arbitrary/shared namespace
operation.

If the marker is absent or mismatched, cleanup fails closed and manual owner
direction is required. No credential, URL, or current project reference belongs
in this repository.
