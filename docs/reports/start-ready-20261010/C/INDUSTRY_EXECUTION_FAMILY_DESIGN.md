### Preserve the existing atomic shape

The actual `AtomicTransitionDraft` contains transition, inventoryPostings, financialPostingBatches, receipt, outboxMessages, currentMaterializations, authorityKind, commitAssertion and observedAtReal. Candidate preparation binds the canonical command, current authorization proof and exact transition; the private constructor cannot be replaced by a JSON-shaped object.

Current repository order is: production schema gate → durable submission lock/existing-final lookup → head/writer guard → current authorization recheck (plus the existing narrow-transfer approval guard only for that family) → Events → inventory postings → financial postings → authorization audit → final receipt → materializations → outbox → queue finalization → head advancement → transaction commit. Failed commit acknowledgement triggers final-receipt recovery, not a fresh economic command.

Industry must use that transaction boundary, without copying narrow-transfer approvals to an unrelated operation or claiming their policy applies. A target update has no inventory/financial posting. A future physical settlement must commit all required authorized effects together or none; a Core proposal, outbox notification or queue FINALIZED status is not proof of those effects.

## 4. One minimal lawful route: Set Utilisation Target

### 4.1 Scope, choices and unresolved serialization

Binding: INDUSTRY U0261, U0280, U0283, U0947. Actor: current Industry office in the facility's country; existing capability INDUSTRY_PRODUCTION. Original operation: **Set Utilisation Target — Facility/Sector + 0–100%**. No Finance/Trade co-signature is specified for this target-setting operation; this must not be generalized to expansion, funding or technology licensing.

Smallest proposed slice is **one existing facility**, not a sector aggregation, new plant or project. Player chooses its target; lowering it can protect scarce input/energy, raising it remains constrained (U0285–U0286). No specific facility is asserted operational in this design.

The product operation is specified, but **there is no existing Industry canonical command tag/parser/Event schema at this base**. Serialization remains UNASSIGNED_PENDING_INDEPENDENT_DESIGN_REVIEW. Do not call an invented `CORE_...` family lawful or already implemented. Likewise, the spec does not settle production scheduling interval, automatic production command tag or the exact target-to-due-run timing; those remain unresolved, not permission to add a clock consumer.

Proposed intent fields (design, not an admitted DTO):

- Existing common envelope: world/country/office, commandId, idempotencyKey, expectedWorldVersion. Server owns actor, authenticated subject, canonical fingerprint, submission time and SimTime.
- `facilityRef`: source-resolved facility identity, constrained to the same country; not a client-created “Riverside” label.
- `targetUtilisation`: canonical `{ amount: string, unit: 'ratio' }` within [0,1], corresponding exactly to the spec's [0%,100%].
- No actualOutput, capacity override, recipe, price, source-ready flag, authority boolean, operating snapshot or client SimTime.

Whether to retain UI percent text until exact server conversion or submit the ratio directly is transport design; use exact decimal arithmetic, not JavaScript `number`. There is no proposed new economic parameter.

### 4.2 Route and source obligations

1. Authorized role projection resolves one real admitted facility and its current target at exact worldVersion/eventSequence/source snapshot. Show missing/unavailable fields honestly. The original prototype does not supply this record.
2. Player reviews old target and selected new target. Target-setting confirmation explicitly says no output is created. Submit once through the reviewed Industry extension of the existing office-command transport; use existing final lookup for uncertain acknowledgement.
3. Intake resolves the current server seat, matching authorization/disclosure/admission/head and registered Industry parser. Reader/composition preflight proves target-bearing facility lineage before a durable claim. Missing source/unsupported schema yields the existing bounded refusal pattern, never a fabricated acceptance.
4. Sole authoritative consumer re-reads the target source at the held head, obtains the normal discretionary authorization proof, and builds a **target-change-only** candidate. Proposed Event semantics carry facility, before/after target and source/head binding. Event type and exact payload/replay schema require review first. Empty inventory/financial posting arrays are correct for this intent, not proof of a production run.
5. Atomic repository rechecks authority/writer/head and persists the target Event, receipt and corresponding derived materialization/outbox/queue/head coherently. Replay must reconstruct the new target from opening+Events and detect duplicate/conflicting intent. New target is not copied into a second authoritative Office store.
6. Only a separately reviewed production interval/due-command path can subsequently read that target alongside actual operating facts and invoke V13. It must bind immutable inputs to current WorldVersion/SimTime and use the same writer/ledger. This phase stays HOLD until section 5 closes.
7. Server-filtered Industry projection distinguishes **committed target change** from **committed physical settlement**. Target before/after may be shown only from its validated Event/receipt. Actual output, material/energy use and bottleneck must come from a settled/replayed result, not from the saved target, a client preview or event counts.

### 4.3 Traceable numerical causality without fabricated world data

Only explicit boundary choices from U0283 are used; no illustrative facility stock, price, recipe coefficient or capacity is fabricated.

Let C be source-owned operational capacity (output unit per duration unit), d the actual reviewed interval in that duration unit, p source-owned unit-preserving productivity, and u the chosen ratio. Existing kernel computes:

```text
P(u) = C × d × u × p
r_material = min over materials of min(1, available / required_at_P)
             (zero required contributes 1)
b = min(r_material, r_energy, r_labour, r_logistics)
Q(u) = P(u) × b
consumed_i = required_i_at_P × Q/P   (scale 0 when P=0)
```

Here ratios/requirements must be recomputed from admitted recipe and availability for the chosen potential, not carried over from a different target. Maintenance and spec/display gaps below still block production admission.

| Player choice sourced from [0%,100%] | Exact kernel consequence for valid explicit facts                                               | What may be claimed                                                                                                                                                                                                                                      |
| ------------------------------------ | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0% → ratio amount `"0"`              | P=0; Q=0; proposed consumption scale=0 and all V13 proposed consumed quantities=0               | Intent can lower the target; no production posting is created. Existing posting constructor **rejects zero output**. This does not zero recurring maintenance costs, refund funding, restore stock or decommission the facility.                         |
| 100% → ratio amount `"1"`            | P=C×d×p; Q=P×b≤P. Every shortage can constrain actual output and each recipe input is tied to Q | This requests full target utilisation, not full delivered output. Without actual C/d/p/recipe/availability/maintenance/permission/funding, a numerical nonzero result is SOURCE_UNAVAILABLE. No factory, price or operating assumption is supplied here. |

For Q>0 the existing posting constructor additionally reproduces material/energy/labour/logistics requirements from positive dimensional coefficients at P, reproduces settled operating cost from costPerOutput×Q, debits actual material accounts and credits the output account. Funding replay must resolve the exact authoritative expense debit and cash/deposit credit; merely naming a batch is insufficient.

**Unresolved numerical evidence is explicit:** this candidate demonstrates the lawful choice, exact zero boundary and source-bound nonzero dependency chain; it does not demonstrate a real country's nonzero production run. Such a worked receipt cannot be supplied from the named specs/kernels alone because they contain no admitted operating snapshot. Substituting test vectors or prototype data would violate this task.
