2026-11-16，Asia/Shanghai。候选 `189a511c5124bcad1a457710442634286417e731`，分支 `codex/office-next-connections-20261108`。

**结论：现在先不购置或升级服务器来解决本次问题。读取负载可以正常运行；一条写入与单会话读取并行时也能复现 503，应先处理读模型发布期间的可用性。100 人完整混合负载尚未通过，不能据此正式开放该规模或签长期服务器订单。**

公开部署仍需要常驻 Node 后端运行环境。待问题修复后，可先按量或按月验证 **2 个持续 vCPU、8 GiB 内存的应用实例，数据库沿用独立托管方案**；这是预留启动、操作系统及部署重叠的试验规格，不是本轮已验证的生产容量，也不是必须马上购买的配置。当前无需购置实体服务器或引入额外服务。

## 失败意味着什么

混合负载中出现 `CURRENT_FINANCIAL_UNAVAILABLE`、`CURRENT_SOCIAL_UNAVAILABLE` 和 `CURRENT_INDUSTRY_LABOUR_UNAVAILABLE`。单会话对照复现的是 Financial 和 Industry 两类。HTTP 返回 `retryable=false`。写入和持久回执成功，随后读取恢复，说明失败与写入过程中的读取可用性相关；**这不是只有 100 个并发请求才出现的问题。**

源码中，当前分页读取会核对投影版本、覆盖证明和实际 World head；不满足时必须拒绝返回。API 将这些 UNAVAILABLE 结果映射为 503，默认不标记为可重试。观测与提交后投影追赶、读取快照跨版本窗口相符，但本轮没有事务级追踪，不能宣称已唯一定位到某条 SQL。

下一步应由 API / Worker 读取与投影 owner 补充“真实提交期间持续读取”的回归，区分暂时追赶与来源缺失/撤销，并设计有界、重新校验授权的重试或明确的等待响应。保留现有版本、来源、撤销和 fail-closed 检查；不能为提高成功率而返回未经授权或拼接的旧数据。完成后再跑原 30 分钟混合负载。本轮未修改这些产品逻辑。

## 资源与采购判断

测试 Node/API 与负载生成器共用限额 2 CPU / 6 GiB 的 Linux 容器；PostgreSQL 独立限额 1 CPU / 3 GiB、network=none，仅通过 Unix socket 连接。静态读取阶段 API 平均使用约 **0.09 个 CPU 核**；RSS 从约 1187 MiB 降至 471 MiB，区间约 359–1187 MiB，没有强制 GC。容器全生命周期（含准备和缓存）内存峰值约 4.01 GiB，不能当作 API 的最低内存需求。没有 OOM 或达到 6 GiB 上限的事件。

因此，当前证据不支持“因为 100 人读取而必须购买更大的机器”。增加硬件可能缩短部分处理时间，但不能替代对单会话也可复现的读写可用性问题的修复。

目前冷启动仍需约五分钟，且单进程峰值约 2.37 GiB，不建议直接选 2 GiB 档位。本轮没有做 2/4 GiB 硬限额实验，不能把 6 GiB 环境下的峰值当成其他限额下必然 OOM 的证明。8 GiB 是后续部署试验的保守预留。

当前完整 Node 入口也不能直接按普通 Cloudflare Workers 的规格部署：其每 isolate 内存上限为 128 MB；前端/边界服务与常驻后端应分别评估。[Cloudflare 官方限制](https://developers.cloudflare.com/workers/platform/limits/)

## 方法、纠正及范围

- Windows 用户工作站，Core Ultra 5 125H / 18 逻辑处理器 / 约 31.6 GiB；非独占云基准机。Docker Desktop 29.7.2、WSL2 6.6.87.2、Node 24.20.0、pnpm 12.3.4、PostgreSQL 16.15，冻结锁文件。测试进程 nice=10，按约 2 秒采样进程外 RSS/VmHWM/CPU。
- 在隔离 Linux 容器重建父/子开局、70 份回执和 Office 来源，完整 Core 验证通过，六份关键制品 SHA 与此前报告相同。未连接生产 Supabase，也未使用生产凭证。
- Ubuntu Docker 集成关闭，因此使用单独测试容器；只将测试库的 socket 挂载适配到本任务命名卷子目录。保留固定 PostgreSQL 镜像、网络隔离、NOINHERIT、RLS 和真实 HTTP/事务/单写者链路。
- 初次临时入口因 Node strip-only 不支持 TypeScript 参数属性而失败，改为仅准备/负载脚本使用 transform-types；被测冷进程使用原构建 JS。首次 H0 Industry 读取因临时夹具缺少派生准备而 503，随后按现有 `prepareFreshIndustryH0` 流程补齐 70 国投影和范围，保持 head=0；该准备错误不计为产品容量缺陷。
- 100 虚拟会话对应约每会话每 5 秒一次读，使用两个授权身份，覆盖 Finance、Central Bank、Social、Industry、Trade。不是 100 个独立账户验收。原生测试 host 每池上限为 1；正式 Node 文档的上限为 2，不能直接等同配置。
- HTTP 为本机 loopback，未计公网 TLS、远程数据库 RTT、完整赛季、WorldClock、到期结算、全部 Office 写入和客户端预测。30 分钟混合持续测试、其后的同数据库重启及生产共享数据库干扰测试均未完成。
- 临时诊断脚本会捕获失败并写入 JSON，因此部分进程 exit 0 只表示证据已输出，不表示测试通过；实际 HTTP 结果和 FAILED 状态已原样保留。
- 延迟汇总中，存在错误的场景包含失败响应耗时；不能把其快速 503 当成成功业务延迟。只读 5 分钟是诊断对照，不冒充 30 分钟稳定性通过。
- 不推进 R2 gate，不自行授予 VERIFIED 或独立审查 APPROVED。本轮没有新建、删除或合并 Git 分支，未提交或推送产品变更；原有六份未跟踪 LOG_USAGE 报告保留。
