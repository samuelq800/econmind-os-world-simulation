## 第一阶段：建立最小、可判因的复现

在现有原生 PostgreSQL / 注册 Node runtime 测试体系中扩展用例，先运行一个授权会话持续读，加一条真实预算命令；覆盖 Financial、Social、Industry，另保留 Trade 等页面对照。使用与原报告一致的来源指纹、RLS 和真实命令消费链路。

记录单条命令的接收、入队、消费开始、原子提交、各投影发布完成及页面读取时间；记录非敏感的 World version/event sequence、投影版本、覆盖证明校验结果、derivedPublication 状态和耗时。不要把令牌、私有页面内容或完整业务载荷写入诊断日志。

分别验证三个原因，避免直接猜测 SQL：

1. head 已推进，投影还未完成发布；
2. 一次读取使用了跨版本的 head、scope 或 document；
3. 发布确实失败、来源缺失或权限被撤销。

在测试中用明确阶段同步点复现窗口，而非仅依靠随机 sleep。若延迟发布或发布失败，必须区分经济提交成功与投影未就绪；不得重执行已提交经济命令。

重点入口：

- `apps/world-worker/src/persistence/postwar-office-publication-controller.ts`：afterCommitted 在已提交步骤后调用 publish；检查 retryCommitted 和完整发布结果。
- `apps/world-api/src/integration/postwar-office-runtime-read-service.ts`：读取事务、授权作用域与 UNAVAILABLE 映射。
- `apps/world-worker/src/persistence/postwar-financial-current-projection.ts` 及对应 Social / Industry reader：向上保留可判因信息。
- `database/proposals/postwar-paged-current-projection.sql`：核实实际加载版本与 head/coverage 校验路径；不能仅修改历史 SQL fixture 代替真实修复。
- 既有 publication-controller、current-publication-head-cutoff、finance-social-source-publication-native 及 runtime-read 相关测试。

退出条件：原缺陷可稳定复现，并能以阶段/版本证据区分上述原因；目前尚未达到。

## 第二阶段：按根因做最小修复

优先修复实际发布或一致性缺陷。若是跨版本读取，在现有读取事务内建立一致读取，或重新开启完整读流程；不能复用旧授权搭配新数据。若是发布失败，修复具体原因，并利用现有派生发布恢复路径重试，不新增经济事件或回执。

若确认是合法的短暂发布追赶，再补有界恢复：

- 仅对已确认追赶状态重试，整体设置总时限、次数上限及取消处理，退避等待不持有数据库连接或事务锁；具体预算根据第一阶段耗时确定并写入测试。
- 每次重试重新核对身份有效性、角色/国家/Office 权限、来源与完整版本绑定。授权撤销、来源损坏和永久缺失继续拒绝，不统一改成 retryable=true。
- 超过预算返回明确的“正在更新/暂不可用”契约，必要时由前端展示等待并有限刷新；等待响应不算成功业务读取，不隐蔽无限轮询。
- 不把旧投影冒充 current，不拼接不同版本，不移动或弱化金融原子提交；任何需要改变提交协议的方案单独评审。

API / Worker / 投影持久化 owner 负责核心修复；只有错误契约确实变化时才涉及 world-web 与共享契约 owner。默认无生产迁移、无新权限；若必须调整 SQL、schema 或 grant，补明确迁移清单、隔离演练和 P0 审查。旧客户端消费同一错误契约时须评估兼容性，不顺带修改另一个 econmind-os 仓库。

## 第三阶段：回归和持续混合负载

先通过低负载回归，再做 100 会话压测，避免对已知缺陷重复消耗资源。

### 必须通过的回归

- 正常提交期间，页面最终返回同一合法版本的完整数据；临时等待行为有明确上限。
- 发布延迟/失败后可恢复；永久缺失不会假成功。
- 等待过程中撤销身份/角色/来源，后续读取仍拒绝；跨国家、跨 Office 访问仍拒绝。
- 幂等重试与恢复不新增重复事件、资金或库存变动；已提交回执不被改写。
- 原预算权限修复继续通过；Financial / Social / Industry 均覆盖，不能只修首个报错页面。
- 实际测试失败时退出非零；准备阶段核实 H0 派生数据完整，避免把夹具错误混入结果。

### 100 会话验收草案

以下是本次修复的拟定工程验收目标，不宣称已有正式产品 SLO：

1. 固定版本只读对照 5 分钟，然后 100 会话持续混合读写至少 30 分钟；目标 20 次读/秒、100 条有效预算命令/分钟。确保实际达成注入速率，不能由慢消费悄悄降速。
2. 同时记录原始 HTTP 错误、等待比例、成功读延迟，以及包含重试的用户操作延迟。临时等待不能从分母中删除；不得靠放大超时掩盖故障。
3. 提议成功读取 P95 ≤ 2 秒、P99 ≤ 5 秒；合法操作在规定恢复期限内无最终失败。若实测要求改变此预算，应明确说明取舍，不改统计口径制造通过。
4. 记录命令入队至 FINAL 的 P50/P95/P99、派生可读延迟、真实未完成队列深度和最老命令年龄。消费速率必须跟上输入，队列不能持续增长；历史记录条数不能当积压。
5. 测试后在同一持久数据库重启运行时，检查 World head、事件、持久回执、幂等性和页面读取。之前 H2 快照克隆恢复不能替代此项。
6. 在报告中注明身份数量：原测试仅两个身份承载 100 虚拟会话。若要声称 100 独立用户支持能力，应增加独立授权身份验证。
7. 先固定原规格作前后对照，再在实际部署候选上验证 TLS、远程数据库延迟和资源余量；单机 loopback 结果不等于公网生产容量。

若写入吞吐不能达标，定位真实瓶颈后仅优化相应阶段，再复测。不得未经评估并行化权威写者或直接增加连接池掩盖排队。
