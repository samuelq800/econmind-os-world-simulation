## 0. 本次方案取代什么、不取代什么

用户已选择：保留 EconMind OS 主站，为 World V2 单独建立 GitHub 仓库，重建世界核心，成熟后整合入口；生产目标继续共享现有 Supabase 的身份与组织基础。实际远程仓库、Supabase 环境、域名、生产连接和部署尚未由本文件创建或修改。

本计划取代上一轮“在原仓库内逐步重构 World”的执行位置与迁移路径，不取代 Master、六 Office 和 Constitution 的功能与工程约束。保留旧站不是要求新核心兼容旧系数公式；重写核心也不允许静默删旧路由、历史和产品功能。[S1–S8]

**项目结论：保留产品资产，重写经济内核，隔离开发风险，按世界逐步切换。** 重写预期减少旧模型兼容成本，但仍需真实解决模型接口、账本、权限和运行可靠性。没有依据保证新仓库一定省多少天或多少模型额度。

## 2. 仓库与部署边界

### 2.1 主站旧repo

继续负责主页、内容、教育研究、学校、团队、联盟、Community、Legal、旧世界兼容和历史。只接收必要的安全修复、最小集成桥及经批准的共享数据库发布变更。旧审计的19项发现需针对部署版本核验；不要因为重写就忽视旧站仍在使用的危险入口。[S9]

### 2.2 新repo：建议名称 `econmind-world-v2`

一个轻量monorepo，不再拆18个repo或18个服务。建议目录如下，属于本计划的工程组织建议，不冒充原规范：

```text
econmind-world-v2/
  AGENTS.md
  apps/
    world-web/                 # UI和浏览器状态；无权威经济写入
    world-api/                 # 验证身份、命令、查询、授权投影
    world-worker/              # 世界调度、事件、结算、恢复
  packages/
    contracts/                 # DTO、事件与版本协议
    core/
      kernel/                  # permission/approval/clock接口/validation
      engines/                 # E01–E18，唯一经济实现位置
      orchestration/           # ordinary world / season
    registries/                # 单位/商品/部门/技术/项目/Office
    persistence/               # DB访问、posting、原子提交、lease
    integration/               # 现有身份与学校团队的只读适配
    ui/                        # 经过依赖审查的纯视觉组件
    testkit/                   # 有出处的fixture、时钟、RNG、断言
  db/
    baseline/                  # 共享schema版本参照，不是第二条生产发布链
    migrations/                # V2领域SQL候选及唯一版本号
    fixtures/                  # 合成用户/团队/初始账户，禁止真实用户数据
  tests/
    architecture/
    domain/
    database/
    security/
    replay/
    e2e/
    performance/
  docs/
    sources/
    architecture/
    decisions/
    requirements/
    runbooks/
    progress/
```

Web/API/Worker是职责边界。API和Worker可先部署在同一服务器的独立进程/容器，不必一开始采购三个云服务。生产Worker不能依附某个浏览器在线，也不能被构建平台的短任务冒充长期世界运行器。

建议保持TypeScript及现有React/Next视觉生态，降低复制组件成本；版本在V00核验并锁定。长计算用独立Worker。数据库继续Postgres。初期不用Redis、Kafka、Kubernetes；只有压测证明连接、队列或缓存瓶颈，且正确性路径不变，才引入额外组件。

平台事实：静态Next导出不提供依赖请求期服务器的动态能力；Supabase托管Edge的CPU限制与wall-clock存活时间不同。[W7/W8] 因而独立Worker是本计划的部署建议，而不是声称已经压测证明Edge必然不足。

### 2.3 可以复用与禁止照搬

复用候选：色板、排版、卡片、图表、表格、导航交互、国家元数据和经过审查的测试工具。每项建立旧path/hash→新path→修改→测试的登记，移除未使用的旧数据hooks与权限绕过。

不复制为新权威逻辑：按hash生成actual的createCountry、GDP直接系数buff、2小时模拟日、只推进状态不交付的合同逻辑、会绕过新版批准的RPC、将世界整行广播的订阅。旧经济模型可以在旧模式继续存在，但不准混入V2正式世界。[S9]

## 3. Supabase共享方式：共享身份，独立世界数据

### 3.1 三层环境

**Local/CI：**本地Supabase或一次性隔离数据库；合成身份、测试seed，可reset，禁止拿生产用户或生产凭证跑测试。

**Staging：**独立Supabase project或符合当前套餐条件的隔离branch，部署完整Web/API/Worker；有与主站schema一致的合成身份数据。压测和恢复演练在此进行。

**Production：**正式批准后接入原Supabase项目，复用Auth及允许的组织数据，V2经济实体独立命名空间。共享的仍是同一个数据库资源池，不是性能或故障隔离。[W1–W4]

### 3.2 数据所有权

|数据|权威owner|V2权限|
|---|---|---|
|认证账号|原Supabase Auth|验证身份；不得在新系统复制密码库|
|profile/school/team/league membership|现有主站指定模块|仅读所需字段，经批准接口消费；不复制为第二套事实|
|V1世界与历史|旧World系统|运行期间不写；可经专用接口显示历史|
|V2世界/国家/角色分配/审批|新repo领域代码|按V2权限核验读写|
|V2库存/账户/债务/产权/技术/合同|各canonical Engine+posting边界|服务器权威命令；浏览器无直接写权限|
|V2events/receipts/outbox|统一事件及事务层|事件append-only，回执/消费状态独立实体|
|summary/cache/snapshot|明确的派生owner|非独立事实；可重建、不反写|

建议使用`world_v2`私有schema保存核心实体，独立授权查询/RPC层提供必要读取。名称在ADR-16确定。**schema名称不是安全边界的充分条件**，必须同时检查grants、RLS、函数EXECUTE、search_path和服务端授权。不能照搬教程中的GRANT ALL给所有客户端角色。[W4/W5]

### 3.3 最容易忽略：同一个Supabase只能有一条受控migration发布链

V2新仓库不能建立不完整的独立migration history后，直接对原共享项目执行`db push`。Supabase依赖本地和远端迁移历史进行比对；这不是“我只改world_v2所以不会影响别人”的问题。[W2]

**推荐首期方案：现有主站repo继续是共享Supabase的生产migration发布源。** V2 repo生成带固定ID/hash的SQL候选，先在匹配共享baseline的隔离环境验证，再通过主站的专门数据库PR纳入同一完整迁移历史，由唯一受控发布流程执行。文件字节与hash必须一致，不能维护两份可分叉版本。

V2 repo负责其schema设计与审查，生产DDL执行权仍集中。后续要转交到专门数据库repo，必须另做一次带历史基线的迁移，不临时“双主发布”。Local/CI的装配说明和生产清单统一来源；禁止为压绿CI使用migration repair假报已应用。

开发自动化不持生产DB凭证；生产运行角色与DDL角色分离。V2 runtime不应拥有旧world/shared表的任意写权。RLS的service/secret角色绕过能力必须明确，不能“打开RLS”就认为worker自然受限。[W5]

### 3.4 Auth、域名与身份撤销

首期新World可用独立子域名，复用同一个账号但允许重新登录，先把真实会话验证做正确。无感跳转另设集成验收，不能假设同Supabase天然共享不同origin的session。[W6]

同源`/simulation`反向代理是后续整合选项，需要实际部署支持、basePath/资源路径/回调/cookie/cache验证，不能只写一行DNS就算实现。严禁把长期access/refresh token放在URL。缓存含Set-Cookie或私人页面的响应会产生会话泄漏风险，需按官方规则隔离。[W6]

用户登录不代表拥有任意国家和Office权限。角色必须绑定world/country/office；成员撤销需要影响新命令与私人投影。已生效合同是国家义务，不能因用户退出自动消失。用户删除与不可变审计冲突需ADR-20：不允许on-delete-cascade抹掉经济历史，也不无依据长期保留额外个人信息。

## 4. 核心运行协议

```text
浏览器提交Command
→ API验证身份、Office、世界、对象、版本、单位与币种
→ 持久化Command及接受回执
→ 按规则取得必要Office审批
→ 单世界writer按确定顺序执行
→ 引擎在隔离候选状态计算
→ 库存/人口/账本/国民账户检查
→ 数据库原子提交经济变更+事件+回执+outbox+版本
→ 授权读投影和Realtime
→ 浏览器看到已提交版本
```

### 4.1 只有一次经济事实，没有“网络永不重复”幻想

命令应至少记录command_id、payload_hash、actor、acting_office、world/country、expected_version、模拟时间、现实审计时间、规则版本与回执。重复网络投递正常处理；保证的是相同经济事实不会再次生效，不是声明所有网络只传一次。

同ID同payload：返回原receipt及ALREADY_PROCESSED/executed=false等批准语义，不再次记账。同ID异payload：拒绝。失败记录不通过改写旧事件实现。事件处理状态位于独立consumer receipt，不UPDATE append-only ledger。细节按ADR-11批准。

### 4.2 候选状态与提交

数据库canonical实体与对应事件/分录在同一受控事务修改；两者不是独立可写的两套余额。Core内存是候选计算，不是丢失即丢世界的唯一状态。Private checkpoint只用于恢复，不对玩家发布半天或半笔结算结果。

建议一个world在一个逻辑时刻只有一个publisher。lease用于识别当前writer，fencing token让已过期的旧进程即使恢复也不能提交。不同world以后可并行。无需先把每国拆成独立数据库再发明分布式事务。

长计算不在持锁事务里反复等待外部API；短提交再验证世界版本与fencing token。若冲突，按批准重算/排队策略处理，不能覆盖别人的更新。通知与缓存失败不会倒过来取消已正确提交的经济事实，由outbox重试。

### 4.3 确定性

固定输入、按权威顺序排列的commands/events、seed、engine/model/registry/scoring版本及同一数值策略，核心结果才要求一致。现实日志时间不混入经济状态hash；ID生成/迭代顺序/并发撮合必须有稳定规则。

不能用新engine版本重放旧日志后要求结果自动相同。升级需明确迁移、兼容或旧版本重放；快照保留不得截断唯一可恢复的账本事实。

### 4.4 后台有结算，玩家没有回合

Master要求连续异步世界。立即规则、订单撮合、精确到期事件和日结必须区别处理。玩家不需要等“下一轮”才能签约；日结也不能跳过已到期付款。[S1 §2]

10×是模拟钟映射，不是每秒重复算18引擎，也不是每次任意跳10天。1模拟日=8640现实秒；1模拟年=360模拟日。UI只显示模拟日期时间、10×、规则生效时间、状态和回执，不暴露Round/Stage/Tick倒计时。

日结阶段与Engine编号必须分别定义。Master E01是Time & Event；E18把National Accounts、Risk、Scoring组合。之前把Time漏掉并将风险单列成第18个的目录写法不再采用。Constitution与Master具体phase表差异保留ADR-01待裁定，不悄悄改原文。

## 5. 规范裁决与可以立即动工的范围

原有15项ADR仍全部是PROPOSED_NOT_APPROVED。第一优先是01阶段、02owner、03Clock边界、04期初/滞后读取、05在途/所有权、09审批。扩充生产与账户前必须处理06供给闭合、07施工核算、08价格精度；国际全类型前处理10；正式公开前处理12–15。

新仓库新增16共享DB/migration owner、17持久化与提交模型、18运行环境与资源隔离、19域名/Auth/cache、20账号/成员撤销与历史保留。详见`02_架构裁决与数据库协议.md`。

**现在可以做：**创建本地脚手架、放入完整规范和只读索引、声明仓库边界、设置不含生产密钥的环境、建立真正运行的lint/typecheck/unit/build、提交未批准ADR和测试计划、复用纯视觉组件。无需把所有经济公式裁完才建立仓库。

**现在不该做：**绕开未决owner创建全数据库；默写农业/医药供给；自行重排phase；默认Captain强制拨款；为画出图随意填真实财政或人口；向生产写migration；把未实现engine返回0或success。

## 6. 从基础到全引擎的七阶段

### S0｜安全启动：V00–V02

产物是能安装、构建、测试、识别环境的新repo，完整需求与ADR、共享身份接口和唯一迁移发布协议。旧站保留，危急授权补丁在旧repo另开小PR。

Gate G0：克隆后的运行说明有效；没有生产自动连接；源规范hash可核对；待裁定项真实列出；没有重建主站其他模块。

### S1｜纵向闭环：V03–V10

先做类型/单位/registry、权限审批、E01、Command/Event、库存及金融posting、原子提交和读取投影，再完成双国一笔真实交易。

采用一个固定目录商品和一组已批准的测试结算条款。测试初始钱和货有明确opening来源和分录，不需要为测试伪造完整GDP。交易必须走UI/API/审批/库存/支付/事件/回执/投影，不能脚本直写结果。

Gate G1：有钱有货能完成；没钱/没货按定义失败；双卖只允许合法占用；重复提交不双扣；worker在commit前后中断可恢复；两国刷新后读同一已提交版本。通过只代表切片通过，不代表18引擎完成。

### S2｜实体经济与人类系统：V11–V17

先人口/技能/人员，再资源与能源/生产；项目/技术同时建设真实设施与权利；教育医疗住房治安接同一项目/劳动/支付内核；家庭接已到账收入和实际消费。

供应链输入必须说明opening/current/prior/scheduled来源。资源与E10统计映射不得重复开采。粮食、国内服务、建设与医疗耗材目录缺口必须经批准闭合，不能无限seed粮食维持测试。

Gate G2：工厂受原料/电力/人员/技术/物流限制；建设消耗真实投入；公共服务有人员和物资积压；家庭不花未到账的钱；账户与实物核对。破产、短缺可以是合法模拟结果，不是拿clamp抹掉的问题。

### S3｜财政金融和全球网络：V18–V24

基础posting在S1就存在，本阶段补齐Finance、CB、FX完整工具和全部国际履约。E16不能只是合同状态机，要23个子类型各有经济执行器，并映射Trade附录的现货、资本管制和Industry技术交流等活动家族。

E18不是最后才开始研究GDP；S1起就记录每笔经济流的核算归属，S3做全部口径核对、风险和只读评分。Captain治理与Admin因果危机在此完整整合。

Gate G3：至少能端到端重现进口短缺→实际生产受限→收入和税收变化、项目融资→建设→运营、贷款→存款→还款、FDI/技术权利/贸易条约的真实影响；其余全类型按需求账验收，不能因三个故事通过就称全量完成。

### S4｜完整产品与70国：V25–V28

六Office界面从S1薄界面开始随领域接入，不等此阶段才写页面。此阶段补齐每个动作、参数、版本审批、失败回执、报告和帮助；多政策组合forecast是授权的非权威分支；机密信息不能从forecast或Realtime反推出。

70国先在开发中逐步扩展2→少量国家→70，不为每国硬编码buff。初始化有资源、人员、设施、资金和供应链一致性。无人国家控制器遵守同样预算和审批规则。

普通World Simulation与Season运行相同Core，分别处理加入/运行/结束语义；其他League活动不因此重做。新世界clean seed，旧指数世界保留历史与明确model_version。

Gate G4：六Office全部已承诺动作有真实闭环，所有23国际子类型与目录都有验证，不存在假actual、空按钮或前端自算正式榜单；70国seed平衡；两orchestrator及旧入口兼容通过。

### S5｜证据驱动验证：V29–V30

70国×600模拟日覆盖正式赛季，另做1000日长跑；加速只改变测试钟推进，不改变正式经济语义。混入大量动作、集中到期、冲击、断线、重试、审批变更和故障。

压测同时跑API授权、DB事务、全核心、Realtime和预测，不能只请求首页或旧系数函数。先50→100→420活跃会话，并分别报告观战、命令频率、订单/合同/事件存量；420不是420个世界，也不代表必须每人在线。

Gate G5：P0/P1无未解释失败；真实RLS/DB/E2E/重放/并发/恢复测试执行；披露机器/套餐/版本和p95/p99；共享DB下主站的关键流程仍满足批准预算；容量不足先减非必要推送/改索引/增资源，不能删事务或RLS。

### S6｜灰度交付与运营：V31–V32

冻结release manifest及seed/registry/model/scoring，先兼容migration/API再前端，内部测试world灰度，最后批准新正式世界和主站入口切换。试验世界与正式榜单隔离。

季末先禁止新动作并按批准截止结算已到期事项，保留未到期债务、合同和在途物。旧世界不能因路由换了就突然停服。UI回切只能退入口，不能把V2已生效经济事实交回旧引擎计算。

Gate G6：正式部署、恢复、管理员和玩家手册、最终覆盖报告、未完成清单、运营负责人齐全；正式环境达到全量gate才称完整交付。

## 8. 30天冲刺如何使用

D1是实际启动日，不是本文件创建日。30天是RC冲刺窗口；完整交付承诺由功能和gate决定，不能反向删范围以满足日历。

## 9. Codex工作规程

每次仅一个工作包或一个可独立验收的子PR：读取相关规则→列计划/文件→确认依赖→实现→实际测试→独立review→演示→合并→更新证据。共享schema/账本/审批/时间接口只能由一个集成人维护，领域与UI任务读固定版本契约。

建议最多同时运行3条互不写同一基础接口的工作流：核心/领域、产品/接口、测试/审查。任务依赖未合并前，下游只能写contract tests或显式mock组件，不能当真实集成完成。

根AGENTS.md保持短，链接完整规范和当前任务；子目录加局部边界。官方Codex支持按目录读取AGENTS.md，默认项目指令读取有大小限制，不能把整套Word硬塞根文件后假设每次都被加载。[W9]

PR必须提交：需求ID和原文来源、读写/事件、schema与migration、权限/审批、事务/回放、真实命令输出、已跑/未跑测试、影响旧站范围、迁移与恢复、未完成项。审查模型的PASS不是测试PASS，测试文件存在不是测试运行。

状态至少为UNASSESSED / SPECIFIED / IMPLEMENTED_UNVERIFIED / VERIFIED / BLOCKED / DEFERRED_WITH_APPROVAL。只能附环境、commit、测试命令和结果后标VERIFIED。源码行数、页面数、聊天长度和创建多少engine目录都不作为完成率。

## 10. 性能、运行成本和故障预算

分开统计开发模型用量和生产云资源账单。生产负载由world数、国家、动作频率、订单/义务、到期峰值、预测频次、DB写、事件保留和Realtime扇出决定，而不是注册用户总数。

提议首轮负载：1world/70国/420活跃会话，每人30秒一条命令约14条每秒；另做集中报价与到期突发。这是明确的测试假设，不是使用现状。记录普通读、accepted、settled、日结、outbox lag和恢复耗时；验收阈值需在V30以实际硬件和产品等待容忍度冻结。

对共享生产数据库额外限制worker连接池、交易超时、每世界队列预算与预测并发，观察主站登录、Teams、内容访问是否受到影响。先减少过大payload/逐字段写入/无范围广播，再测是否升级资源。

Worker崩溃后的幂等恢复不等于数据库灾难RPO=0。备份、WAL/PITR是否可用和保留多久取决于实际配置；V30必须真实恢复并记录RPO/RTO，不只检查面板有备份标记。
